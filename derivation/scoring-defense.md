# Защита скоринга: почему заголовок — среднее с флагом, а не минимум

**Статус:** черновик на утверждение Виктора. Не публиковать, не переносить в `docs/methodology.md` без решения.

Раздел отвечает на главную атаку методолога-эксперта традиции CMMI/ISO 33000: «зрелость определяется слабейшим звеном; staged-модель не даёт уровень N, пока не закрыт уровень N−1, а у вас среднее арифметическое — статистическая подделка, прячущая провалы за витриной хороших цифр».

---

## 1. Что считается сейчас

Три формулы, дословно из шапки рубрики:

> «headline-стадия (гибрид) = round(mean(cluster_avg)); слабое звено (min cluster_avg) показывается отдельно» — `rubric/stage-map.yaml:1`

> `stage_rule: "round(mean(cluster_avg))"` — `rubric/stage-map.yaml:5`
> `weak_link_rule: "argmin(cluster_avg)"` — `rubric/stage-map.yaml:6`

Тот же алгоритм повторён в `meta.scoring` рубрики:

> `scoring: "per-cap levels; weakest-link flagged; headline stage = round(mean(cluster_avg)); weak_link = argmin(cluster_avg)"` — `rubric/aist-pos-rubric.yaml:10`

И в шаге скоринга воркфлоу:

> «`cluster_avg` — среднее уровней способностей направления. В каждом направлении пометь слабое звено: способность с минимальным уровнем. `headline_score` — среднее по `cluster_avg` всех направлений; `headline_stage` — округление к ближайшему, имя стадии из `stage-map.yaml`. `weak_link` — направление с минимальным `cluster_avg`.» — `workflows/assess.md:66-70`

Три уровня агрегации, каждый со своим усреднением:
1. `cap_level` — уровень способности (1–5), ставится по ответу человека.
2. `cluster_avg` = среднее уровней внутри направления (18 способностей → 5 направлений).
3. `headline_score` = среднее пяти `cluster_avg`; `headline_stage` = округление к ближайшей стадии.

Что видит человек первой строкой выдачи — по `workflows/assess.md:76`:

> «**Стадия**: имя, N из 5 и описание из карты стадий; можно показать дробную оценку.»

Второй строкой — не среднее, а диагноз:

> «**Что подтянуть первым**: слабое направление и почему это критический путь.» — `workflows/assess.md:77`

То есть слабое звено не спрятано — оно идёт сразу за заголовком, отдельной строкой, до профиля целиком.

## 2. Три альтернативы на двух профилях

Беру рубрику как есть — 18 способностей в 5 направлениях (`rubric/aist-pos-rubric.yaml:12-386`):

| Направление | Способности | N |
|---|---|---|
| context | memory, context_seed | 2 |
| files | naming, root_file, git, source_map, handover | 5 |
| capture | connectors, capture, graph | 3 |
| work | doc_source, playbook, quality, output_form, autonomy | 5 |
| knowledge | research, decision_log, sign_off | 3 |

Считаю стадию тремя правилами на одних и тех же пяти `cluster_avg` — заменяю в формуле `mean` на `min` (минимум = приближение к CMMI staged: не получаешь кредита за успехи, пока не закрыто самое слабое) и на `median`. Оговорка к этому выбору — в §5.

| Способность | Направление | Уровень |
|---|---|---|
| memory | context | 2 |
| context_seed | context | 1 |
| naming | files | 1 |
| root_file | files | 1 |
| git | files | 2 |
| source_map | files | 1 |
| handover | files | 1 |
| connectors | capture | 1 |
| capture | capture | 2 |
| graph | capture | 1 |
| doc_source | work | 1 |
| playbook | work | **3** |
| quality | work | 1 |
| output_form | work | 1 |
| autonomy | work | 2 |
| research | knowledge | 1 |
| decision_log | knowledge | **3** |
| sign_off | knowledge | 1 |

12 единиц, 4 двойки, 2 тройки — «много единиц-двоек, пара троек», как заказано.

`cluster_avg`:
- context = (2+1)/2 = **1.5**
- files = (1+1+2+1+1)/5 = 6/5 = **1.2**
- capture = (1+2+1)/3 = 4/3 ≈ **1.333**
- work = (1+3+1+1+2)/5 = 8/5 = **1.6**
- knowledge = (1+3+1)/3 = 5/3 ≈ **1.667**

- **Минимум**: min = 1.2 (files) → round(1.2) = 1 → стадия 1, «Первые опыты».
- **Среднее (текущее)**: (1.5+1.2+1.333+1.6+1.667)/5 = 7.3/5 = 1.46 → round(1.46) = 1 → стадия 1, «Первые опыты».
- **Медиана**: отсортировано [1.2, 1.333, 1.5, 1.6, 1.667], средний элемент = 1.5 → round(1.5) = **2** → стадия 2, «Помощник».

Для новичка минимум и среднее совпадают (стадия 1). Медиана — единственная из трёх, что расходится, и расходится не в сторону строгости, а в сторону мягкости: она поднимает человека, у которого 16 из 18 способностей на уровне 1–2, на стадию «Помощник». Причина механическая: медиана из пяти точек берёт ровно средний по порядку `cluster_avg` и полностью игнорирует хвосты — в том числе игнорирует files=1.2, самое слабое направление, которое как раз и должно тянуть диагноз вниз.

| Способность | Направление | Уровень |
|---|---|---|
| memory | context | 3 |
| context_seed | context | 3 |
| naming | files | 3 |
| root_file | files | 3 |
| git | files | **4** |
| source_map | files | 3 |
| handover | files | 3 |
| connectors | capture | 3 |
| capture | capture | 3 |
| graph | capture | 3 |
| doc_source | work | 3 |
| playbook | work | 3 |
| quality | work | **4** |
| output_form | work | 3 |
| autonomy | work | 3 |
| research | knowledge | 3 |
| decision_log | knowledge | 3 |
| sign_off | knowledge | 3 |

16 троек, 2 четвёрки (git, quality) — «все тройки, пара четвёрок».

`cluster_avg`:
- context = 3.0, capture = 3.0, knowledge = 3.0
- files = (3+3+4+3+3)/5 = 16/5 = **3.2**
- work = (3+3+4+3+3)/5 = 16/5 = **3.2**

- **Минимум**: min = 3.0 (три направления связаны — context, capture, knowledge) → round(3.0) = 3 → стадия 3, «Оператор».
- **Среднее**: (3.0+3.2+3.0+3.2+3.0)/5 = 15.4/5 = 3.08 → round(3.08) = 3 → стадия 3, «Оператор».
- **Медиана**: отсортировано [3.0, 3.0, 3.0, 3.2, 3.2], средний = 3.0 → стадия 3, «Оператор».

Здесь все три правила сходятся на стадии 3. Это тоже содержательный результат: когда профиль ровный (ни одно направление не проседает), выбор агрегатора не имеет значения — расхождение между «минимум», «средним» и «медианой» появляется только там, где профиль неровный. Иначе говоря: спор об агрегации — это спор именно про неровные профили, не про ровные. Побочный факт этого расчёта: у минимума здесь трёхсторонняя ничья (context = capture = knowledge = 3.0) — `argmin` без явного правила разрешения ничьей формально должен выбрать любой из трёх; для заголовка-стадии это не важно (все дают одно и то же round), но для «слабого звена» как отдельного направления — важно, и `weak_link_rule` в `rubric/stage-map.yaml:6` такого правила не содержит. Это открытый вопрос, а не решённый факт.

### Третий профиль — где альтернативы реально расходятся

Ни новичок, ни практик не показывают то, ради чего вообще спорят про агрегацию: случай «сильный почти everywhere, ноль в одном направлении». Добавляю его как дополнительную иллюстрацию сверх заказанных двух профилей — потому что без неё защита выглядела бы так, будто я избегаю самого острого случая.

Все способности на уровне 4, кроме направления `files` (naming, root_file, git, source_map, handover) — там везде уровень 1 (например: человек забросил сохранность и структуру файлов, но по всем остальным направлениям работает зрело):

`cluster_avg` = context 4.0, files **1.0**, capture 4.0, work 4.0, knowledge 4.0.

- **Минимум**: min = 1.0 → стадия **1**, «Первые опыты».
- **Среднее**: (4+1+4+4+4)/5 = 17/5 = 3.4 → round(3.4) = 3 → стадия **3**, «Оператор».
- **Медиана**: отсортировано [1, 4, 4, 4, 4], средний = 4 → стадия **4**, «Дирижёр».

Вот здесь разница настоящая: минимум топит человека на стадию 1 несмотря на то, что 4 направления из 5 у него зрелые; медиана делает обратное — вообще не видит провал (14 способностей из 18 — четвёрки, а «файлы» полностью на нуле, и это никак не отражено в стадии); среднее — единственное из трёх, что и показывает движение вниз (3, а не 4, потому что files действительно тянет), и не убивает всё достижение целиком (3, а не 1, потому что остальные четыре направления реальны). Именно на этом профиле видно, почему «медиана» — не более честная альтернатива, а менее чувствительная: она реагирует на слабое место только когда оно не единственное. А «минимум» реагирует всегда — но ценой того, что не различает «ничего не сделано» от «всё сделано кроме одного».

### Сводная таблица

| Профиль | Минимум (CMMI-style) | Среднее (текущее) | Медиана |
|---|---|---|---|
| Новичок (16 из 18 на 1–2) | стадия 1 | стадия 1 | стадия 2 (!) |
| Практик (все на 3, пара 4) | стадия 3 | стадия 3 | стадия 3 |
| Сильный everywhere, files=1 | стадия 1 | стадия 3 | стадия 4 (!) |

Что сообщает каждая альтернатива и чем платит:

- **Минимум**: сообщает «у вас есть узкое место — вот на каком уровне вы реально застряли». Платит тем, что не различает степень остального профиля: человек, у которого закрыто 4 направления из 5, и человек, у которого не закрыто ни одного, получают одну и ту же стадию 1 (если хоть одно направление — на нуле). Для аудитории руководителей это буквально стоп-сигнал уже на первой строке, независимо от реального объёма работы, — то, от чего явно уходит `stage-map.yaml:7-9` (см. §3).
- **Среднее**: сообщает «в среднем по системе вот такой уровень» и реагирует на любой провал пропорционально его размеру относительно остального профиля. Платит тем, что число само по себе не называет, какое именно направление слабое, — поэтому оно всегда идёт в паре с явным флагом слабого звена (см. §1, вторая строка выдачи).
- **Медиана**: сообщает «типичный уровень направления» — но именно поэтому она устойчива к выбросам, что здесь работает против диагностики: единственный провал в меньшинстве направлений (1 из 5) вообще не виден в итоговой стадии, а для новичка она парадоксально мягче среднего. Медиана — не более строгая версия среднего, как можно было бы ожидать по интуиции «медиана устойчивее к выбросам», а версия, слепая именно к тому единичному выбросу, который и является предметом атаки.

## 3. Почему выбрано среднее с флагом

Первый аргумент — из решения, уже записанного в самой рубрике, дословно:

> «Заголовок стадии человек видит первой строкой выдачи, и на короткой оценке первую-вторую стадию собирает большинство. Прежнее имя первой стадии читалось как приговор, а не как начало пути — для аудитории руководителей это стоп-сигнал.» — `rubric/stage-map.yaml:7-9`

На минимуме («CMMI-style») это давление не снимается, а усиливается: профиль «сильный everywhere, files=1» из §2 при чистом минимуме получает стадию 1 — тот самый приговор, от которого дизайн стадий сознательно уходил, при том что у человека реально зрелых 4 направления из 5. Заголовок на минимуме превращается в наказание за одно упущение, а не в честную сводку прогресса, — и именно от такого прочтения предостерегает комментарий автора в шапке.

Второй аргумент — диагностика слабого звена не потеряна, а перенесена из заголовка во флаг, который показывается всегда:

> «слабое звено (min cluster_avg) показывается отдельно — см. stage-map.yaml» — `rubric/aist-pos-rubric.yaml:4`

> «**Что подтянуть первым**: слабое направление и почему это критический путь.» — `workflows/assess.md:77`

Разница с CMMI staged не в том, есть диагностика слабого места или нет, — она есть в обеих системах. Разница в том, где она стоит: в CMMI staged слабое место *определяет* заголовок (заголовок и есть min), в AIST POS слабое место стоит *рядом* с заголовком отдельной строкой сразу после стадии. Ни одна деталь, которую даёт «минимум», не потеряна при переходе на среднее — она просто не единственное число на странице.

## 4. Поведение на границах округления

Дробная оценка видна человеку — это прямо разрешено:

> «**Стадия**: имя, N из 5 и описание из карты стадий; можно показать дробную оценку.» — `workflows/assess.md:76`

То есть `headline_score` (например, 3.4 или 1.46 из профилей §2) — не скрытое внутреннее число, а часть легитимной выдачи.

- **2.5** и **3.5** — оценки ровно на границе. `stage-map.yaml:3` определяет правило как `round(mean(cluster_avg))` с пояснением «(к ближайшему)», но не говорит, куда округляется *ровно* половина — вверх, вниз или к чётному. В `workflows/assess.md` та же формулировка без уточнения (`assess.md:69`). Кода, реализующего скоринг, в репозитории нет — скоринг делает LLM-агент по текстовому правилу воркфлоу, а не детерминированный скрипт (проверено: `grep` по `.py/.js/.ts/.sh` на `round`/`cluster_avg`/`headline` не находит ни одного файла реализации). Значит, поведение на самой границе сейчас не определено источником правды, а зависит от того, как агент интерпретирует слово «round» в моменте.
  - Граница достижима не только теоретически: `headline_score` — среднее пяти чисел вида «сумма уровней / размер направления» (знаменатели 2, 3 или 5), и стандартный случай, дающий ровно `X.5`, — например, все пять `cluster_avg` равны 2.5 (профиль, где в каждом направлении половина способностей на уровне 2, половина на уровне 3).
- **3.49** — не граница, округляется однозначно вниз, до 3. Двусмысленности здесь нет ни при каком общепринятом правиле округления.

Практическое следствие: пока в `stage-map.yaml` не появится явное правило для ровной половины (вверх / вниз / к чётному), для профилей, чей `headline_score` попадает точно на `X.5`, стадия на границе не гарантированно воспроизводима между прогонами одной и той же рубрики. Это отдельный, самостоятельный гейт-кандидат (не предмет данного раздела — раздел документирует агрегацию, а не правило округления), но защита скоринга не может закрыть его молчанием: эксперт спросит про 2.5 в первую очередь, и честный ответ сейчас — «не специфицировано», а не выдуманное «округляется вверх».

## 5. Ответ на атаку CMMI прямо

Атака дословно (как сформулирована в задаче): «зрелость определяется слабейшим звеном; CMMI не даёт уровень N, пока не закрыт N−1, а у вас среднее арифметическое — это статистическая подделка».

Разница предмета, а не только метода:

- **CMMI staged model** сертифицирует **организацию**: уровень N присваивается только когда для *всех* процессных областей уровня ≤N закрыты специфические и общие практики (институционализация) — это дискретный гейт «выполнено / не выполнено» на каждую практику, а не непрерывное среднее и даже не непрерывный минимум. Важная методологическая оговорка: столбец «минимум» в таблице §2 — это уже облегчённая версия настоящего CMMI staged в пользу критика (я беру непрерывный `min(cluster_avg)` вместо дискретного гейта по практикам), потому что настоящий CMMI staged к нашей шкале 1–5 буквально не применим — у него нет «среднего уровня направления», есть только «удовлетворена практика или нет». Сравнивать с точной механикой CMMI здесь нельзя технически: разные типы данных на входе.
- **AIST POS** — структурированная самооценка личной системы одного человека, где 5 направлений — это разные, не вложенные друг в друга линии развития (память агента развивается независимо от сохранности файлов; агент может отлично работать с документами и при этом не иметь базы контактов). Модель не заявляет, что уровень N в одном направлении логически требует уровня N в другом, и рубрика нигде это не утверждает — это явное заявление, а не спрятанное допущение.

Что AIST POS прямо **не** утверждает (и не должна утверждать, чтобы не наткнуться на ту же критику с другой стороны):
- не аттестация («вы получили сертификат уровня 3») — это диагноз, из которого следует конкретный следующий шаг (`workflows/assess.md:79-83`, поле `do`/`how`/`done_when`), а не допуск к чему-либо;
- не сравнение людей между собой — стадия не рейтинг, у рубрики нет механизма сопоставления профилей разных людей;
- не психометрия — способности не валидировались как психологический измерительный инструмент; это структурированный самоотчёт по описанным поведенческим признакам, ответ ставит сам человек, сверяясь с формулировками `levels{}`.

Итог по существу атаки: возражение «среднее прячет слабое звено» опровергается не спором о статистике, а фактом устройства выдачи — слабое звено показано всегда, второй строкой (§1, §3). Возражение «CMMI требует закрытого N−1» неприменимо, потому что AIST POS не заявляет вложенность направлений друг в друга — а раз не заявляет, то и не обязана вести себя как модель, которая её заявляет.

## 6. Что изменилось с введением трёх ярусов

По решению Виктора от 2026-08-13 ячейка матрицы задача × способность типизирована в три яруса — цитирую формулировки:

> «**Порог входа** (`needs`) — минимум, при котором задача даёт первую реальную ценность; риски допускаются и честно называются. Остаётся узким и различающим.
> **Ярус надёжности** — чем задача взрослеет: без этого работает, но эпизодически подводит или требует ручных подпорок; сюда же «зрелые обещания» (накопление, расписание). Новое поле каталога задач.
> **Гигиена системы** — защищает все задачи сразу (сохранность, конфиденциальность и т.п.): слой модели, а не ячейки задач.» — `specs/2026-08-13-model-audit-design.md:79-81`

Это решение уже реализовано в данных, не только в спеке. В `rubric/job-sets.json` у каждой задачи, помимо `needs` (порог входа), есть отдельное поле `hardens` (ярус надёжности) — пример на задаче «День начинается с одной сводки»:

```
"needs": { "autonomy": 4, "capture": 3, "connectors": 3, "playbook": 3, "quality": 3 },   // job-sets.json:28-34
"hardens": { "capture": 4, "connectors": 4, "quality": 4 }                                 // job-sets.json:35-39
```

И отдельно, на уровне всей модели, а не одной задачи — гигиена:

> `"hygiene": { "level": 3, "caps": ["git", "naming", "source_map"], "why": "защищает всё построенное сразу, а не отдельную задачу: тот же сценарий отказа воспроизводится при любой работе с файлами и данными" }` — `rubric/job-sets.json:291-298`

**Почему это не ломает скоринг из §1–§5.** Три яруса отвечают на другой вопрос, чем headline-стадия. Стадия (§1–§3) считается по `cluster_avg` — среднему уровню способностей внутри направления, по всем 18 способностям рубрики целиком, и не смотрит ни на одну конкретную задачу. Ярусы (`needs` / `hardens` / `hygiene`) — это требуемые уровни для конкретной задачи: они отвечают не «какая у человека стадия», а «готова ли вот эта задача и на каком уровне». Это два независимых среза одних и тех же 18 уровней способностей, не два конкурирующих способа посчитать одно число:

- стадия = функция от профиля способностей (агрегация по направлениям, безадресная);
- готовность задачи = сравнение того же профиля с конкретным вектором `needs`/`hardens` этой задачи (адресная, двухосевая: есть ли первая ценность vs. надёжна ли она).

Косвенное подтверждение того, что это разделение задумано, а не совпадение, — сама Фаза 4 воркфлоу уже устроена так, что план и «главный шаг» считаются не от стадии, а от выбранной задачи и её `needs`:

> «Требуемые уровни под каждую задачу — в `rubric/job-sets.json`; где задаче нужен уровень выше третьего, честно скажи, что за один заход он не берётся» — `workflows/assess.md:82`
> «**Главный шаг**: первое, чего не хватает выбранной задаче, — та её способность, что отстаёт от требуемого уровня сильнее прочих. […] На странице этот шаг считается сам и пересчитывается, когда человек переключает задачу.» — `workflows/assess.md:83`

Иными словами: до введения трёх ярусов «слабое звено» уже существовало на двух разных горизонтах — безадресном (направление с минимальным `cluster_avg`, флаг в Фазе 4) и адресном (способность, отстающая от `needs` выбранной задачи, «главный шаг»). Три яруса не добавляют третий способ считать стадию — они уточняют адресный горизонт: раньше у задачи был один требуемый уровень на способность (`needs`), теперь два (`needs` — порог первой ценности, `hardens` — порог надёжности), плюс отдельный, общий для всех задач слой гигиены. Формула стадии (`round(mean(cluster_avg))`) ни одного из этих полей не читает и не обязана — это не тот вопрос, на который она отвечает.

## Самые слабые места этого текста

1. **§4, границы округления.** Честный ответ на «что при 2.5 и 3.5» — «не специфицировано ни в `stage-map.yaml`, ни в `assess.md`, кода-реализации нет». Это правда, но это дыра, а не защита: эксперт-методолог спросит именно про эту границу первой, потому что округление до `X.5` — классическое место, где агрегаты типа «среднее» дают воспроизводимо разные результаты у разных исполнителей (LLM-агент в одном прогоне округлит вверх, в другом — вниз). Раздел не закрывает вопрос, а честно показывает, что он открыт, и это может прочитаться как незавершённость самой модели, а не только текста.

2. **§5, столбец «минимум» как прокси CMMI.** Я сам называю его «облегчённой версией в пользу критика», потому что настоящий CMMI staged — дискретный гейт по институционализации практик, а не `min` от непрерывных чисел 1–5. Это честно, но означает, что вся количественная часть защиты (таблица §2, «минимум даёт стадию 1 при 4 зрелых направлениях из 5») бьёт по модели, которую я сам ослабил под свою шкалу, а не по буквальному CMMI. Строгий оппонент может сказать: «вы спорите не с CMMI, а с его континуальной пародией, которую сами же и построили» — и это будет справедливое замечание, требующее отдельного ответа (например: показать, что дискретный CMMI-гейт на наших данных давал бы ещё более резкий разрыв между «почти всё сделано» и «ничего не сделано», а не более мягкий).
