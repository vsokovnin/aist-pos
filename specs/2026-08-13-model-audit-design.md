# Аудит модели AIST POS — дизайн

**Дата:** 2026-08-13 · **Статус:** на ревью у Виктора · **Автор:** сессия Claude (brainstorming, секции 1–4 одобрены в чате)

## 1. Цель и угроза

Модель (18 способностей × 5 уровней × 5 направлений × 13 задач) масштабируется на публику в форме «продукт + публичная методология»: модель будет называться по имени и объясняться в лекциях и статьях. Главный критик — **эксперт-методолог**; через его удовлетворение получают пользу пользователь и скептик рынка.

**Планка строгости:** методолог зрелостных моделей (традиция CMMI/ISO 33000 — структурная строгость) + практик-методолог (применимость, проверяемая на артефактах). **Психометрия исключена явно:** модель заявляется как структурированная самооценка, не измерительный инструмент; это записывается в методологию, а не скрывается.

**Происхождение модели (факт, со слов Виктора):** рабочие задачи, которые хочется поручить агентам → способности, необходимые задачам → минимальные уровни на задачу. Деривация реальна, но недокументирована. Аудит делает её **воспроизводимой и трассируемой** — это одновременно защита надёжности и ответ на вопрос «откуда 18».

**Конечная цель Виктора:** артефакт, точно описывающий набор способностей и уровней для каждой рабочей задачи, + понятный гайд реализации каждой задачи навыком.

## 2. Фазы

Порядок жёсткий: состав модели (Ф1) проверяется до формулировок (Ф2), чтобы не переписывать тексты дважды.

| Фаза | Содержание | Ключевой артефакт |
|---|---|---|
| 0 | Критерий отбора задач в каталог | раздел в `docs/methodology.md` |
| 1 | Матрица: слепая передеривация + состязательный пас | `derivation/{job}.json` × 13, выверенный `needs` |
| 2 | Рубрика: грамматика ступеней + проход по 18 | `docs/` грамматика, правленая рубрика |
| 3 | Скоринг: защита агрегации | раздел в `docs/methodology.md` |
| 4 | Публичный методологический документ | `docs/methodology.md` |
| 5 | Механические гейты (параллельно Ф1–Ф2) | правки `scripts/pack.sh` + скрипт сертификации |

## 3. Фаза 0 — критерий отбора задач

Одна страница: что делает задачу кандидатом в каталог. Базовая формула (уточняется Виктором): «рабочая задача руководителя, выполнение которой частично или полностью хочется поручить агенту», + признаки отсечения (не проект, не разовая, есть повторяемость и наблюдаемый результат). Без критерия защита «выведено из задач» уязвима ударом уровнем выше: «почему эти 13?».

Черновик готовит агент обратным ходом из существующих 13 (`rubric/job-sets.json`), утверждает Виктор.

## 4. Фаза 1 — слепая передеривация (подход А) + состязательный аудит (подход Б)

### 4.1 Протокол дериватора

На одну задачу — три независимых агента, друг друга не видят, промпт одинаковый.

**Вход:** `title` / `short` / `promise` задачи — **без `needs`**; каталог 18 способностей с полными формулировками пяти уровней из `rubric/aist-pos-rubric.yaml`. Каталог — закрытый словарь: маппить можно только на него, изобретать способности нельзя.

**Выход (жёсткая схема, Workflow structured output):**

- `operations[]` — задача, разложенная на наблюдаемые шаги; у каждого вход и выход;
- `cells[]` — `{operation, cap_id, level, failure_scenario}`; **сценарий отказа обязателен**: «без способности X на уровне N шаг ломается так». Ячейка без сценария не проходит валидацию;
- `gaps[]` — операции, не покрытые каталогом, со сценарием отказа. Механизм обнаружения недостающих способностей без права агента расширять модель.

### 4.2 Сверка

Скрипт (не агент) сводит 3 деривации × 13 задач с текущим `needs`. Классификация расхождений автоматическая:

| Сигнал | Кандидат-вердикт |
|---|---|
| вывели все три, в матрице нет | не хватает способности |
| в матрице есть, не вывел никто | способность лишняя |
| уровни разошлись | уровень определён неверно |
| `gaps[]` | в каталоге нет способности |

Каждый кандидат — агенту-судье с одним тестом: подтверждается ли сценарий отказа формулировками рубрики и обещанием задачи. Вердикт с обоснованием → **очередь решений Виктору**. Ни одна правка `needs`, состава способностей или каталога задач не вносится без его решения (propose-before-promotion).

### 4.3 Пас Б

После решений Виктора, по обновлённой матрице: на каждую задачу четыре стандартных атаки (чего не хватает / что лишнее / уровень занижен / завышен), каждый вердикт — со сценарием отказа или контрпримером. Ловит симметричные пропуски слепых дериваторов.

### 4.4 Критерии приёмки фазы

- у каждой ячейки `needs` есть трассировка до операции со сценарием отказа;
- неразрешённых расхождений ноль (по каждому есть решение Виктора);
- сходимость опубликована честным числом (§6, тест 8) — вместо недоказуемых «99%».

### 4.5 Механика

Workflow, батчи по 4–5 задач (13×3 дериватора + судьи + пас Б); между батчами — точки контроля Виктора.

## 5. Фазы 2–4

### 5.1 Фаза 2 — рубрика

**Грамматика ступеней** — центральная находка дизайна. Подлежащее уровней в рубрике меняется по ступеням, а не по способностям: L1–L2 — человек делает руками; L3 — заведено и работает; L4 — человек видит сбои и правит; L5 — система поддерживает себя сама. Это неписаное генеративное правило; записанное, оно даёт ответ на вопрос «почему уровень N сравним между шкалами»: ступень N значит одно и то же во всех 18.

Артефакт — одна страница в `docs/`: семантика каждой ступени + форма вопроса (развилка исхода, запрет дословного эха вопрос↔варианты) + территория и «не про что» каждой способности.

**Проход по 18** — проверка соответствия грамматике, не вкусовые споры. Известные нарушения (найдены на способности 02): L3 с подлежащим-человеком («я ему следую», `rubric/aist-pos-rubric.yaml:59`), L5 с действиями человека внутри «само» (`:61`), дословное эхо вопроса в L1 (`:55`→`:57`), рецепт не про предмет вопроса (`:63-66` про постоянные вводные при вопросе про материалы под задачу). Замер эха по всем 18 (скриптом, против первого варианта): у 8 способностей дословные общие 2-граммы вопрос↔вариант. Правки предлагаются пачкой, решение по каждой — Виктора.

### 5.2 Фаза 3 — скоринг

Защита против стандартной атаки «зрелость = слабейшее звено; CMMI не даёт уровень N без закрытого N−1, у вас среднее». Решение фактически принято (`rubric/stage-map.yaml:7-10`: мотивирующий заголовок + честный флаг слабого звена, заголовок не занижается), но не защищено как выбор. Оформляется: таблица «минимум / среднее / медиана» с последствиями для аудитории руководителей; поведение на границах округления; почему диагностика слабого звена переехала из заголовка во флаг, а не потерялась. Готовый текст проходит короткую состязательную проверку агентами.

### 5.3 Фаза 4 — методологический документ

`docs/methodology.md`, публичный, пакуется с навыком. Порядок разделов = порядок вопросов эксперта: критерий отбора задач (Ф0) → трассируемая деривация состава (Ф1, ссылки на `derivation/`) → грамматика ступеней (Ф2) → защита скоринга (Ф3) → границы применимости (структурированная самооценка, не психометрия — заявляем сами) → позиционирование против существующих рамок (короткий внешний ресёрч: CMMI/ISO-традиция, PKM, agentic-maturity модели; раздел «чем отличаемся и почему осознанно», без претензии на выведенность из чужих рамок).

## 6. Сведение и тесты устойчивости

**Сведение.** Детерминированный скрипт собирает 13 файлов `derivation/` в матрицу-кандидат с происхождением каждой ячейки: операции, дериваторы, сценарий отказа, решение Виктора. Дифф против `needs` → очередь находок → после решений — выверенная матрица с полной трассировкой.

**Критическое противоречие** определяется явным списком; устойчивость = ноль по каждому классу:

1. **Покрытие** — ни одной операции без способности; все `gaps[]` разрешены. Механический.
2. **Минимальность** — каждая способность нужна ≥1 задаче. Механический. *Уже красный на текущей матрице: `git` не требуется ни одной задаче в `needs` — открытый вопрос §8.*
3. **Межзадачная согласованность уровней** — разные уровни одной способности у разных задач трассируются в разные операции. Полумеханический: расхождения находит скрипт, оправданность судит агент.
4. **Согласованность с грамматикой ступеней** — сценарий отказа ячейки требует ровно того, что означает её ступень (сценарий «само по расписанию» в ячейке уровня 3 — противоречие: это ступень 4). Агентный, по записанной грамматике. Стык Ф1×Ф2.
5. **Целостность лестницы** — рецепт есть для каждого требуемого перехода (`to_L3` у всех, `to_L4` где просит матрица). Гейт существует (`scripts/pack.sh:66-77`), обязан остаться зелёным после обновления матрицы.
6. **Уникальность территории** — одна операция ложится на одну способность во всех задачах; пересечение = вход Ф2 (правка «не про что»). Механический.
7. **Смоук обещаний** — ни одна задача не требует невозможного профиля; «базовый круг» (все на 3) даёт непустой набор готовых задач; требования уровня 4 честно видны. Механический.
8. **Сходимость и воспроизводимость** — доля ячеек, независимо выведенных ≥2 из 3 дериваторов (публикуемая метрика); выборочный повторный прогон 1–2 задач свежими агентами после правок — матрица неизменна.
9. **Выживание под атакой** — пас Б завершён, неразобранных подтверждённых атак ноль.

**Форма результата.** Тесты 1, 2, 5, 6, 7 — скрипт сертификации в репозитории; отчёт воспроизводим кем угодно, включая эксперта. Тесты 3, 4, 9 — агентные, вердикты фиксируются файлами рядом с трассировками. Публичное утверждение: *каждая ячейка подтверждена сценарием отказа и независимой деривацией; девять классов противоречий проверены, неразрешённых ноль; проверка воспроизводима скриптом из репозитория.*

## 7. Фаза 5 — гейты

В `scripts/pack.sh` после аудита (чтобы выправленное нельзя было молча сломать):

- **Гейт направлений:** `clusters[].caps` ≡ полю `cluster` по содержанию. Сейчас сверяется только количество (`pack.sh:17-19`); реальное расхождение проходит молча: `connectors` числится в `capture` (`rubric/aist-pos-rubric.yaml:21`), а в самой способности `cluster: files` (`:150`).
- **Гейт эха:** ноль общих 2-грамм между `ask` и формулировками уровней.
- **Гейт трассировки:** каждая ячейка `needs` имеет запись в своём `derivation/{job}.json`.
- Грамматика ступеней механизируется частично (словарь маркеров: «сам/сама» вне L5 и т.п.); остальное — ревью. Ограничение называется честно.

## 8. Открытые вопросы Виктору

1. **Способность `git` без задачи** (тест 2 красный уже сейчас): добавить задачу, которой нужна сохранность («ничего не теряется и восстанавливается») / завести явный класс «гигиенических» способностей, нужных системе, а не задаче / исключить способность. Решение определяет, как формулируется минимальность в методологии.
2. **Критерий отбора задач** (Ф0) — черновик будет предложен, финальная формулировка ваша.
3. **Судьба «13»** — числа задач и способностей могут измениться по итогам Ф1; все числовые упоминания в документах держит существующий гейт (`pack.sh:22-34`).

## 9. Размещение артефактов

`pack.sh:124-139` копирует в пользовательский пакет фиксированный список, включая `docs/` целиком. Поэтому:

- **публичное** → `docs/`: `methodology.md`, грамматика ступеней;
- **внутреннее** → `specs/` (этот документ), `derivation/` — в `ITEMS` не входят, в пакет не попадают; на GitHub видны — трассировки усиливают защиту («проверяйте сами»).

## 10. Вне охвата

- Психометрическая валидация на данных пользователей (исключена решением Виктора).
- Воспроизводимость стороннего оценщика-человека — форма (в), «передача метода», не планируется.
- Подход В из обсуждения (канонизированная библиотека операций как слой модели) — YAGNI при 13 задачах; операции живут внутри файлов деривации без отдельного слоя.
